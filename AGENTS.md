# Repository Layout (Nx monorepo, pnpm)

- `apps/web/` — Next.js 15 dashboard, API routes and the in-process publish scheduler (`pnpm dev:web`, `http://localhost:3434`)
- `apps/mcp/` — MCP server (npm `post-engineer-mcp`, stdio; tests via `pnpm exec nx test mcp`)
- Root commands: `pnpm test`, `pnpm lint`, `pnpm typecheck`, `pnpm build`

## Workflow

- Never push to `main` — always open a PR. Small, focused PRs; CI green and review threads resolved before merge.
- **Beta: breaking changes are acceptable and preferred over backward-compat dual paths.** The product is in beta with zero real users (only the owner and a test account), so delete the old path instead of deprecating it or maintaining both paths — a deprecation window or dual-path shim is tech debt until real users exist. DB migrations still need care. When the first paying user arrives, this rule flips explicitly (a user decision): deprecation + migration window become mandatory.
- TDD by default: every change ships with new/updated tests; the relevant suite is green before committing.
- **File-size ratchet (CI `file-size`): files already over the 500-line cap are grandfathered and may not grow by a single line** — a feature that adds lines to one must extract existing code into a new small module in the same change so the file ends at or below its base size (precedents: `apps/mcp/src/schedule-shapes.ts`, `apps/web/lib/publisher/` helpers, route-sibling modules like `app/api/persona/form-parsing.ts`). Check before pushing: `node .github/scripts/file-size/check.mjs --base <merge-base> --head HEAD`. Generated `*.gen.<ext>` files are exempt from the file-size check; each must be pinned by a drift test against its generator. Vendored CalendarCN files are exempt too (`.github/scripts/file-size/vendored-calendarcn.mjs`, pinned to upstream `6e15924d`): third-party code — their line counts are upstream's, and the same list scopes Stryker (never mutates them), the UI coverage gates (not our UI), and Codecov (`codecov.yml` `coverage.ignore`, pinned to the list by `vendored-calendarcn.test.mjs` — the patch gate would fail on their uncovered lines otherwise).
- **Run the file-size check after the final commit, before pushing (2026-11-10, PR #529 lint).** The check measures `--head HEAD` (committed), so running it before the last commit measures the previous HEAD and misses the new growth — `post-metrics.ts` crossed the 500-line cap (383 → 503) in a commit made after the check ran, and CI's lint failed on it. Commit first, then check, then push.
- **Verify a branch still merges with `git merge-tree --write-tree`, not plain `git merge-tree`.** Plain output carries no `<<<<<<<` markers, so grepping for them reports a false clean while real conflicts exist (PR #497 sync: 8 conflicts missed). Use `git merge-tree --write-tree --merge-base=$(git merge-base HEAD origin/main) HEAD origin/main` and grep `^CONFLICT`.
- **MCP parity gate — never weaken it.** Every `apps/web/app/api/**/route.ts` handler must be reachable by an agent through an MCP **intent tool**: a registered tool whose action (or the tool itself, for a tool without actions) really issues that method + path, mapped as `endpoint → { tool, action }` in `apps/mcp/src/__tests__/parity-endpoint-tools.json`, proven from the syntax tree (the action's own handler reaches the request site) and, for an action, by invoking it (`parity-action-samples.json`). **A tool is a complete abstraction of an intent — never add a tool, or an action, just because an endpoint exists:** one action may call several endpoints, and an endpoint that is only a step of an intent (a resolver lookup, a preview folded into its confirm step) is mapped to the action that calls it. The alternative to a mapping is a typed exclusion in `apps/mcp/src/__tests__/parity-exclusions.json`, verified per handler from the syntax tree and by a behavioural bearer test. Never add, edit, or re-label an exclusion, or edit the parity test, its `parity/` verifier, the bearer test, the guard or CODEOWNERS, to make a failure go away — the fix for a parity failure is an action on the right intent tool (registered by its `intent-*.ts` module, mapped, given sample arguments in `parity-action-samples.json`, documented and tested). Such a PR fails `parity-exclusion-guard` until the code owner approves the current head and applies the `parity-exclusion-approved` label; never apply that label yourself.
- **No dead code (CI `dead-code`, `pnpm lint:dead-code`).** Three gates, all blocking: **knip** (`knip.ts`) fails on an unused file, export, exported type, duplicate export or dependency in apps/web, apps/mcp, `scripts/` and `.github/scripts/` — an export only its own file uses loses the `export`, a symbol nobody uses is deleted; **`.github/scripts/dead-code/contracts.mjs`** does the same for `shared/contracts/` (knip cannot see it: the apps import gitignored copies), where an export must be used by web, mcp or another contract; **vulture** (`.github/scripts` Python) fails on unused functions, classes, constants and attributes. `noUnusedLocals` is on in both TypeScript configs, so a local the cleanup leaves behind fails typecheck. `pnpm lint:dead-code:fix` drops needless `export`s; delete what is left by hand. Code used only by its own tests is dead too: vulture enforces that for the CI scripts (it scans no tests), knip counts a test import as a use, so in TypeScript delete such code by hand with its tests. Vendored CalendarCN files, `*.gen.ts` and the code-owned parity files are exempt from the export checks only (an unused vendored *file* still fails); never widen `ignoreIssues`, `ignore_names` or the entry lists to make a finding go away.
- **No copy-pasted code (CI `duplication`, `node .github/scripts/duplication/check.mjs`).** jscpd scans production TypeScript, TSX, JavaScript and Python (apps, `shared/`, `scripts/`, `.github/scripts/`; tests, generated and vendored files are out) and fails on any block of 10+ lines and 100+ tokens that appears twice. The fix is one shared function or module, never a tweak that only breaks the token match. Shared helpers so far: `lib/oauth/social-start.ts` + `social-callback.ts` + `session-user.ts` (social OAuth routes), `lib/connect-fields.ts` (key-connect routes), `lib/supabase/env.ts` + `request-client.ts`, `routeErrorResponse` in `lib/api-error.ts`, `app/(main)/accounts/provider-accounts-section.tsx` + `use-key-connect.ts`, `components/legal-page.tsx`, `lib/docs/slug-page.tsx`, `.github/scripts/cli/args.mjs`. A route the parity verifier reads by syntax (an `oauth-redirect` or `bearer-rejected` exclusion) keeps the checked call in its own file (`setOAuthNonceCookie`/`oauthPopupResponse`, `requireSupabaseSession(request)` and the 403) and moves only the rest. Never raise `minLines`/`minTokens` in `.jscpd.json` or add an ignore to make a clone pass; the thresholds are pinned by `check.test.mjs`.
- **One provider list — the `provider-lists` lint (`.github/scripts/provider-lists/check.mjs`) fails CI on a hand-typed provider list.** `shared/contracts/providers.ts` holds `SOCIAL_PROVIDERS`, every named subset and the per-provider contract maps (`PUBLISH_ACCOUNT_FIELDS`, `SCHEDULE_ACCOUNT_COLUMNS`). Outside it, an array/union/tuple/`Literal` of 3+ networks fails, a per-provider ternary/if/switch chain fails (use `Record<SocialProvider, …>`), and a map or select string that names 3+ networks must name all of them (`null` entry when a network has nothing to do) or exactly a named subset. A new subset is exported there. Never add a per-file exemption to make it pass.
- **Look at the UI you changed.** After editing `apps/web`, load the `preview-ui` skill (`.opencode/skills/preview-ui/SKILL.md`) and check the running dev server — screenshots, both locales (PT is default), console. Never schedule a real post or spend tokens for a screenshot.
- **UI PRs get before/after screenshots from ui-diff, not manual shots.** After editing `apps/web`, load the `ui-diff` skill (`.opencode/skills/ui-diff/SKILL.md`, vendored from upstream `imuratalpay/ui-diff`, commit `3075b4c8`, with two local patches in `SKILL.md`: the PR-body step and the public-repo rules) and run it on the PR: it captures base vs head on desktop + mobile and diffs with pixelmatch. **The before | after | diff images go in the PR body (`UI changes` section) — the sticky comment is never a substitute for the body.** Publish the images first (`publish`; the owner allowed publishing to this public repo on 2026-11-22, so `apps/web/ui-diff.config.json` sets `publish.allowPublicRepo: true` and no `--allow-public-repo` flag is needed) and link the published URLs in the body; when publish is not possible, attach the images in chat so the owner can drag them into the body. Only publish screens with no private data: the images are public. Every capture masks `[data-ui-diff-mask]` — on `AccountCard` names, emails and avatars, the signed-in user's sidebar and mobile-header profile links, and `PersonaAvatar` — plus `data-testid` selectors that already exist on `main` so base captures are masked too; mark any new element that shows a person's or an account's identity the same way, pinned by `lib/__tests__/ui-diff-config.test.ts` and the component tests. Logged-in screens use the E2E session cookie (`auth` in `apps/web/ui-diff.config.json`; `auth.origins` must list both `http://localhost` and `http://127.0.0.1`, the runner answers on either loopback). Run with `TMPDIR` on disk (`/tmp` is a 512M tmpfs and fills during the two `pnpm install`s). Never `--motion` (no animated GIFs).
- **Screenshots in a PR body — the exact recipe (2026-11-21).** GitHub has no API for drag-and-drop image uploads (upstream `references/privacy.md` says so verbatim) — the only automatable way is pushing the images to the repo's own `ui-diff-assets` orphan branch and pasting the raw URLs in the body. Steps: `run` → `publish --pr <n>` (the config allows this public repo) → copy the URLs from the publish output → `gh pr edit <n> --body-file` with a `UI changes` section, one block per changed route → verify the body shows the section and the URLs. No browser login is needed anywhere in this flow (git + `gh` only). When publish is impossible — no write access (fork / read-only token, exit 3), no remote, GitHub down — attach the composites in chat so the owner drags them into the body (drag-and-drop in the web UI is the manual route; only a human in a browser can do it).
- **UI PRs are not merge-ready without before/after screenshots in the PR body.** Any change to what the user sees — layout, styling, or copy — fills the `UI changes` section of `.github/pull_request_template.md`: before and after shots of the same screen, same locale, same viewport, plus mobile shots when the layout changes and both locales when copy changes. A PR that only changes copy still needs the shots; a green test suite says nothing about layout.
- **Every PR body includes an Excalidraw before/after diagram.** It explains the change, not the UI: left = problem before, right = solution after. Excalidraw style — white background, sketchy stroke, in English, with colors — and the agent draws it itself and uploads it as a real GitHub attachment (`https://github.com/user-attachments/assets/…`) with `gh pr edit <n> --attach <png>` (needs gh ≥ 2.99; check `gh --version`, the apt gh is older). Never commit it and never push it to `ui-diff-assets`, which is for ui-diff screenshots only. This is distinct from, and in addition to, the UI screenshots above.
- **Versioning is generated at deploy time; never bump by hand.** `VERSION` holds only MAJOR.MINOR (edited when cutting a release line). Deployed version = `MAJOR.MINOR.PR_NUMBER`, resolved on the VPS from the merged PR of the deployed commit (deploy fails if unresolvable). No version commits/PRs. The root `package.json` version is hand-maintained and independent. **The MCP version is generated too, and the web accepts exactly that one version:** `MAJOR.MINOR` from the same `VERSION` file (so a PR touching `apps/mcp/` ships web and MCP as the same number; `apps/mcp/package.json`'s version is ignored) + the ordinal of the last commit touching `apps/mcp/` in main's history (`.github/scripts/mcp-release-version.sh`, e.g. `1.53.219`; history order is merge order, so an out-of-order merge cannot lower it — a PR number does, and #655/#661/#662 stalled the deploy that way on 2026-11-19). `release-mcp.yml` publishes it to npm (trusted publishing, no token) on every `apps/mcp/` merge and re-checks on a best-effort schedule (GitHub throttles the 10-minute cron to hours) — a failed publish heals on the next tick or on `gh workflow run release-mcp.yml`, no bump PR, no version commit. The VPS deploy computes the same version as `REQUIRED_MCP_VERSION` and deploys the web only once npm serves it; the web answers any other `X-MCP-Version` with 426 `MCP_VERSION_MISMATCH` naming the exact version (`apps/web/lib/mcp-version-gate.ts`). Change the version rule in both repos together, or the web waits for a version that is never published. Build metadata (`VERSION`/`PR_NUMBER`/`BUILD`/`COMMIT`) is reported by web `/api/version`.
- After a rebase touching any `package.json`, run `pnpm install --frozen-lockfile` locally before pushing and diff the dependency blocks (conflict resolution has silently dropped deps and duplicated `"version"` keys).
- After merging/cherry-picking commits made in the GitHub web editor, run the affected tests + typecheck locally.
- Commit messages describe the implementation, not the process ("redact encoded app password", never "review 11 findings").

## Chat replies

- **Every summary the agent posts in chat ships with a spoken version.** Render the summary as MP3 with the local CPU TTS and attach it next to the text in the same reply. Never run that work inside the live `mpt-tts-cpu` container — the deploy recreates it and kills in-flight jobs. Run a one-off container from the same image instead: `docker run --rm -v tts_models:/models -v tts_voices:/voices -v <script>:/tmp/tts.py:ro -v /tmp/opencode:/out mpt-tts-cpu:latest python /tmp/tts.py`, where the script calls `local_tts.backends._use_system_espeak()` then `kokoro.KPipeline(lang_code="p", repo_id=backends.KOKORO_REPO, device="cpu")` with voice `pf_dora` (pt-BR).
- The rule is a reply format, not a code path: no route, tool, or fixture changes it.

## Language

- **No code comments (CI `comments`).** Source files (`*.ts`, `*.tsx`, `*.js`, `*.mjs`, `*.cjs`, `*.py`) carry no comments: name things so the code explains itself, and put the why in the PR body or the docs. Only tool directives stay, and **a directive carries only the directive** (`.github/scripts/comments/directives.mjs`): `// eslint-disable-next-line rule` with no `-- reason`, a bare `// @ts-expect-error`, `// @vitest-environment node` with no `: why`, `# noqa: CODE` / `# type: ignore[code]` / `# pragma: no cover` with no trailing prose, `// codeql[id]` with no explanation, and JSDoc `@type`/`@param {T} name`/`@returns {T}` in plain JS with no description. The directive must start the comment; a comment that only mentions one is a plain comment. **Blanket suppressions fail** (`@ts-ignore`, `@ts-nocheck`, an `eslint-disable` with no rule, a bare `# noqa`, `# type: ignore` or `# pyright: ignore`), and so does **suppressing a correctness or safety rule** (`ESLINT_CORRECTNESS_RULES` / `PY_CORRECTNESS_CODES` there, e.g. `react-hooks/exhaustive-deps`, `no-explicit-any`, `no-floating-promises`, `F821`, bandit `S*`, `nosec`): fix the code instead. Both ESLint configs set `ban-ts-comment` to `'ts-expect-error': false` so a bare `@ts-expect-error` passes, while `@ts-ignore` still fails. Find them with `pnpm lint:comments`; `pnpm lint:comments:fix` strips comments and directive prose, but never a blanket or correctness suppression. Docstrings are not comments: FastAPI reads them into `openapi.json`. Generated, vendored and code-owned parity files are exempt. Test names are in English.
- **Every review finding that describes an invariant of the code becomes a gate — never a one-off fix.** A review bot (opencode) or a human finding that names a pattern the code must never repeat ships with the narrowest gate that stops it, and the PR that fixes the finding pins it (negative control: revert the fix, the gate must fail). **A regression test is the default.** Promote it to a repo-wide checker only when the pattern is a true invariant — a rule that holds for every file, not just this incident — and then the checker must pass the whole repository in the same PR: if it needs a new `allowlist.json`/`exclusions` entry, the pattern was an incident, so drop the checker and keep the test. Rationale: a hand-fix dies with the file move, and a global checker that needs exceptions converts one incident into a permanent list. When a finding cannot be pinned mechanically (judgement call, runtime-only state), say so in the PR body and carry it as a sentence in the reply — never silently extend the list of hand-fixed items, and never encode an unverified reviewer claim as a gate.
- Everything public on GitHub (PR/issue titles and bodies, review comments) is in English.

## Env files (never commit secrets)

- One env file: `apps/web/.env` (incl. Cypress `E2E_TEST_EMAIL`/`E2E_TEST_PASSWORD`). Gitignored; created from `apps/web/.env.example`. No new env files, no `.env.local`.
- Never remove `.env` ignore rules, stage secret files, or print secret values.
- **No fallback values for env vars** — fail explicitly when missing (`process.env.X!`, never `|| 'default'`).
  - Exception: PostHog keys (`POSTHOG_API_KEY` / `NEXT_PUBLIC_POSTHOG_KEY` / `NEXT_PUBLIC_POSTHOG_HOST`) are warn-and-continue — telemetry must never break the app.

## Code standards

- No `any`; use `unknown` + type guards. Explicit function types. Avoid type assertions.
- Strict null checks: spell out `=== null || === undefined`; `== null` is banned. Falsy is not absent (`''` is a provided value).
- Server actions use `'use server'`.
- Never fail silently: log errors, surface explicit messages, never catch-and-suppress. Mutations treat non-2xx, non-JSON, and `success:false` as failures; invalidate caches only on real success.
- When a flow is removed, delete the whole path (route, client fns, MCP tool, docs, i18n keys, tests). Unused code shouldn't exist.
- When fixing a flagged pattern, grep the whole repo for siblings (callers and callees) before calling it fixed.
- Test names, docstrings, and docs must describe what the code actually does — update them in the same change.
- Pin the same literal everywhere it lives: values duplicated across files/apps (SQL limits vs TS constants, cross-app copy) get a file-parsing sync test. No dynamic `new RegExp(interpolated)` even in tests (CodeQL) — use `includes`.
- A new gate or check on stored data must accept every form the product already stores, not just the current canonical one: personas store language as a code (`en-US`) or a full name (`English`, see the edge-tts name map), and the English-only gates in web/MCP initially rejected the name form (PR #252 review). Before adding a validator, grep the other subsystems for the forms they already accept.
- This repo pins a specific Next.js version: check `apps/web/package.json` and `node_modules/next/dist/docs/` before framework-level code.

## Web UI

- `apps/web/components/ui/` = presentational components (props + callbacks); keep fetching/OAuth/state outside.
- **Reuse before you build (strict).** Look in order: `components/ui/` (shadcn; add primitives with `pnpm dlx shadcn@latest add <x>`), `components/` (`account-card.tsx`, `provider-icon.tsx`, `ui/social-accounts-section.tsx`, `ui/insufficient-tokens-dialog.tsx`, `ui/version-badge.tsx`, `ui/token-pack-cards.tsx`), `lib/ui.tsx` (icons, `INPUT_CLASS`, `SECTION_LABEL_CLASS`; compose with `cn()`), `lib/publish-links.ts` (network maps). A second differently-styled version of an existing component is a bug. Justify any new component in the PR.
- Social accounts: React Query via `useSocialAccountsQuery` / `useYouTubeAccountsQuery` / `useInstagramAccountsQuery` / `useBlueskyAccountsQuery` / `useLinkedinAccountsQuery` (`lib/api.ts`), all sharing the single `social-accounts` key (one `GET /api/account`, provider hooks filter via `select`); no parallel `useState`/`useEffect` fetchers.
- Never render raw server/English errors or internal codes in the localized UI — map to i18n keys with a localized generic fallback. User-facing numbers interpolate shared constants.
- **Surface a thrown error's message only when it is an app error, never for a transport failure (2026-11-21, PR #708 follow-up to #704).** A mutation that returns `{success:false}` for HTTP errors throws only on transport failures (fetch `TypeError`), so a catch that surfaces `error.message` verbatim renders raw `Failed to fetch` in the localized UI. Carve out `TypeError` (and empty messages) and fall back to the localized generic key.
- Client fetch helpers never throw on HTTP errors: check `response.ok`, guard `response.json()` (proxy HTML bodies), return `{ success: false, error }`. Every promise chain has a `.catch`.
- UI gates derive from persisted/loaded data, not create-flow (zustand) stores. Disable every control while a mutation is pending. No side effects inside setState updaters. Effect deps key on ids, not objects.
- Destructive dialogs: initial focus, Escape, focus trap, reset on close.
- Overridable base classes go through `twMerge`. `next/image` `priority` only for real LCP images.
- Metadata icons: config `icons` disables file-convention icons in this Next version — declare every role; keep icon files small.
- A dynamic `import()` doesn't keep Node-only packages out of the client bundle — use `/* webpackIgnore: true */`. CI doesn't run `next build`; reproduce with `npx nx build web --skip-nx-cache`.

## Web API

- Validate strictly: 400 on over-length, malformed, conflicting, or coerced input — never silently truncate/coerce/drop. Validate shared params before branch splits; cheap checks before expensive reads.
- Unknown ids → 404. At `.single()`: PGRST116 → 404, any other error → logged 500. Never discard a query error on an auth/security branch.
- Classify failures: 404 = truly gone; 401/403 = config error (log at error, never retry); 5xx/429/aborts/unparseable-200 = transient (retry with backoff).
- Service-role bypasses RLS: re-check ownership explicitly. API-key **and** OAuth callers take the service-client branch (`isApiKey === true || isOAuth === true`).
- supabase-js `rpc()` never throws — always destructure and check `error`.
- Multi-step DB mutations go in one SQL function with locks; check-then-act re-checks in the UPDATE predicate (zero rows → 409).
- A committed mutation is never a bare 500: return what committed plus stable warning codes. Warnings are stable codes (`PERSONA_IMAGE_WARNING_CODES`) rendered amber, not red — symmetric across producers.
- Coerce derived state at the write boundary on every branch, including legacy data (e.g. legacy `NULL` `face_mix_percent` coerces unconditionally on every write path).
- Deletes: collect storage paths before cascade; delete rows first, storage after (best-effort, one retry, loud logs).
- Bound fan-out and reads: caps + time budgets, deterministic `.order().limit()`, expose `truncated`. Post-commit cleanup goes in `after()` with its own budget.
- **Every route handler is rate limited (CI `rate-limits`).** Each exported method of every `apps/web/app/**/route.ts` must reach `applyRateLimit` (directly, via a same-file helper, or by passing a `RATE_LIMITS` profile to a helper); an intentional exemption is a typed entry (kind + reason) in `.github/scripts/rate-limits/allowlist.json`, and a stale entry fails too. Reads that API-key/OAuth callers poll use `profileForCaller(auth, CALLER_RATE_LIMITS.x)`, so machines get a small budget and the browser keeps a larger one above the UI's refetch rate. Per-task reads that machines poll (`persona/video-status/[taskId]`, the `persona/video-events/[taskId]` stream) use `applyTaskPollLimit(request, taskPollCaller(auth), taskId, RATE_LIMITS.x)`: one call per minute per (API key or OAuth user, task), with a 429 + Retry-After the MCP waits out; browser sessions are not limited there. `taskPollCaller` requires the key id for API-key callers (an API-key caller without one throws instead of sharing one bucket per user). Mock the limiter in other suites (spread `importOriginal`, override only `applyRateLimit`).
- Insert keys must exist in the schema; NOT NULL-without-default columns must be supplied (schema-sync tests pin both).
- Route files export only handlers. Decode percent-encoded route params before pattern-matching.
- `GET /api/version` reports the web build metadata and telemetry flags; nothing else. There is no external service contract snapshot: the web exposes only its own routes.
- SSRF: server fetches of user URLs resolve DNS and reject any non-public address, fail closed, `redirect: 'error'`, https + timeout; inject the lookup for tests.

## Publishing (web scheduler)

- The publish scheduler runs inside the web process (`lib/scheduler-jobs.ts` + `lib/publisher/`), one slot at a time, bounded by a per-tick cap and a time budget. The SQL claim (`claim_next_publish_slot`) is the only bound on concurrent publishers: never publish a slot without it.
- The route and the scheduler share `lib/upload/publish-content.ts`. A direct handler call would skip the publish ledger, the guard against a resumed slot publishing twice.
- Scrub secrets before truncating, on every surface (telemetry, logs, Discord, stored/client-visible errors, email). Redact known credentials (e.g. webhook URLs) by exact replacement including transport-encoded variants; use the pattern scrubber only for unknown text. Don't scrub typed ints.
- Data-dependent failures fail the item once, not the whole tick. A Supabase outage logs once and stops the rest of the tick, with a reminder every 30 minutes.
- Uploaded videos live in the `videos` bucket (`lib/publisher/constants.ts`); the scheduler signs and downloads them; cleanup runs after a terminal state.

## MCP

- Secrets (bearer tokens, app passwords, URL userinfo, upstream errors) never reach output/logs — redact raw, encoded, and JSON forms; cap upstream bodies.
- HTTPS or loopback-only URLs, normalized; OAuth `auth_url` must be https.
- Empty 2xx → `{ ok: true }`; non-JSON 2xx → error. Every fetch has an `AbortSignal` timeout (files: 120s).
- Tools are intent tools (10, each with an `action`), not one per endpoint. A tool's schema is defined once next to its handlers, registered by its `intent-*.ts` module (index.ts only wires them) with `byAction({ action: handler }, SPECS, 'tool')` (`action-tool.ts`): one flat advertised schema (a root union advertises no fields), a strict per-action re-parse, defaults never on the flat shape. Persona and account fields take a name or an id (`refs.ts`: exact match, candidates on ambiguity, never a guess). Actions that read a local file are offered on stdio only (`unavailable`). Re-parse inside the handler when a `.refine` matters. Shared limits exported from one module.
- Bounded memory: `stat()` before reading files, read sequentially; argument checks before any file read.
- No test-only seams on production interfaces — inject via options (`now: () => Date`).

## Supabase migrations

- Numbered, append-only in `supabase/migrations/` (prefix = apply order); never edit a shipped file. Everything idempotent.
- `create table if not exists` with inline FK never adds the FK to an existing table — add FKs in a `pg_constraint`-guarded do-block.
- Update `supabase/README.md` with each migration — it is the single migration list; `docs/SELF_HOSTING.md` only links to it, never duplicate the list there. Moving a migration file: grep the tests that read it.
- **Never hand-edit `supabase/schema.snapshot.json` (2026-11-11, PR #548).** Regenerate with `dump-schema --write` against a freshly migrated local Postgres and let `--check` verify it: the check diffs text, and `jsonb_object_agg` emits check keys in non-alphabetical order (e.g. the `video_type` check lands right after the primary key), so a hand-ordered edit fails the check.
- CI checks numbering and applies the chain to an ephemeral Postgres (stubs only `auth`/`storage` — extend stubs if needed). BETA: there is no destructive-DDL label gate — destructive migrations are approved by the owner's merge tap, no separate label step; reintroduce the `db:destructive-approved` label gate explicitly when the first paying user arrives (the BETA flip rule). CD runs `supabase db push --linked --include-all` on merge (or via workflow_dispatch, always from `main`), before redeploying the VPS: `--include-all` also applies an older-numbered migration whose PR merged after a newer one, which plain `db push` refuses — without it an out-of-order merge leaves that migration unapplied forever.
- **A provider list lives in every table's check, not just the one the feature touches.** 034 added `'threads'` to the `post_metrics` check but not to `social_accounts`, whose `social_accounts_provider_check` (created by versioned migrations 0015/0016, deleted in the b4037cff consolidation, so the current chain never creates it) still held the four pre-Threads providers, so the Threads OAuth callback upsert failed in production with a check violation. When adding a value to a provider list, check the live database's constraints too — objects the chain no longer defines can linger in prod — update every table's check in the same migration, and pin each list to its TS source of truth with a file-parsing sync test.

## Prompts — they live only in the database

- Every prompt is a row in `user_prompts` (private or public, owned by one account); there are no official prompts and no prompt text in git. The web hub, the detail page `/recipes/[slug]`, and the MCP (`prompts`, slash commands) all read `GET /api/prompts` and `GET /api/prompts/[slug]`. To add or change a prompt, edit it in the app or with `prompts` (action: create or update), never in code.
- Never put prompt text, steps, or a list of prompt slugs in code, docs, or tests as product data — a copy in git drifts the moment the row changes.

## Docs (/docs, /help)

- Docs facts are imported from their source of truth, never retyped: tool names from `TOOL_DESCRIPTIONS`, setup from `buildInstallPrompt`, networks from the providers contract.
- Editing a docs page bumps `updatedAt` and `contentHash` together; the freshness test pins both.

## Testing gotchas

- Tests must not pass vacuously: assert the path under test was actually taken; mutation-verify new pins (revert the fix, the test must fail). Test names match their assertions.
- **A guard test must order its statements so the guarded statement can actually break the assertion (2026-11-21, PR #712 OpenCode MINOR).** The "drop table in a comment is ignored" test put the commented `drop table` *before* the `alter table`, so with comment stripping broken the drop deleted from an empty map and the alter re-added the table — the test passed with the regression present. The commented statement goes *after* the statement it protects, so an un-stripped comment deletes the table and the assertion fails.
- **A "without touching the database" test must assert every query channel, not just deletes (2026-11-17, PR #628 OpenCode MINOR + MAJOR).** The non-UUID DELETE test asserted only `deleteCalls` was empty, so moving the `isUuid` guard below the slots select (or the persona-scope lookup, which filters the same uuid column) would still pass while reintroducing the 22P02 → 500 regression. Assert `selectArgs` and `slotSelectArgs` are empty too — and run the test as a scoped API key, because the scope lookup only runs for scoped keys: with a browser session `selectArgs` is trivially empty and cannot fail.
- **Test fixtures must use relative dates, never fixed future dates (2026-11-15, PR #599 CI).** `publish-existing/route.test.ts` hardcoded `expires_at: '2026-11-15T12:00:00Z'`; once the clock passed noon UTC, `loadReadyVideoUpload` threw 410 VIDEO_UPLOAD_EXPIRED and the three ready-upload tests failed in CI — while they had passed hours earlier when the date was still in the future. Derive fixture dates from `Date.now()`; a fixed future date is a time bomb, and a test that passes in the morning and fails in the afternoon is the symptom.
- Mocks mirror production (real query chains, real envelopes, echoed payloads).
- Env in tests: `vi.stubEnv(key, undefined)`, never `delete process.env.X`; stub/clear every related var (CI injects ambient ones like `BUILD`). Don't `mockReset()` a `vi.stubGlobal`'d fetch in `beforeEach`.
- Multipart route tests need `// @vitest-environment node`.
- Logger migrations preserve the exact console call shape (`msg, obj`).
- Web tests resolve repo files via `findRepoRoot(import.meta.url)` (`apps/web/test/repo-root.ts`), never `process.cwd()` (Stryker runs from `.stryker-tmp`).
- Stryker mutates the PR's changed LINE RANGES on web/mcp (`path:startLine-endLine` — `.github/scripts/ui-gates/changed-ranges.mjs` parses the `-U0` diff and emits the escaped patterns; new files and fallbacks mutate whole, so the scope only widens). Bracketed paths still need `[[]`/`[]]` escaping — done inside changed-ranges.mjs; a new file or a fallback mutates the whole file, so the scope only widens.
- JWT tamper tests flip the first signature char, not the last.
- Cypress: specs end with `export {};`; log in via `cy.loginE2EUser()`; only `cy.wait()` on requests the app actually fires; the AppShell renders hidden responsive twins — scope selectors to a visible container and exact hrefs; set React inputs via the native value setter + `input` event; binary fixtures need `'x.mp4,null'`; never fake `setTimeout` with `cy.clock()` on React Query pages.
- **CI Cypress never talks to the production Supabase project (2026-11-23).** The `cypress` and `cypress-coverage` jobs start a throwaway local stack (`.github/actions/local-supabase`, config `apps/web/cypress/supabase/config.toml`), apply `supabase/migrations/` and seed the E2E user with `apps/web/cypress/supabase/seed-e2e.sh` — running the suite against production made CI half of that project's billed log ingestion. A spec that needs a row the API mocks cannot provide gets it from the seed script, never from production secrets. Mock API responses with the shared helpers (`cypress/support/prompt-mocks.ts`): a hand-built body that misses a field the client's zod schema requires renders the error state (prompts-hub, #729).

## CI / review

- Don't pass flags via `pnpm <script> -- <flags>` in workflows (pnpm forwards a literal `--`); use `pnpm exec <bin>`.
- API naming lint (`.github/workflows/api-naming.yml`) checks only new names in the contract surface; never rename shipped fields to satisfy it.
- Local review is `opencode run --agent reviewer` (or the reviewer agent in the TUI) with a free model (`opencode/nemotron-3.5-lightning-free` or `opencode/flint-40b-free`, no key needed). The default/build agent does not review. CI runs the same agent on every `REVIEW_MODELS` entry in parallel (`opencode-review.yml`: `opencode/nemotron-3.5-lightning-free`, `opencode/flint-40b-free`, `openrouter/nvidia/nemotron-3-ultra-550b-a55b:free`, 12 minutes each) and keeps the first review that ends with a Verdict line, because free models hang at random; pass 2 races the entries that did not win pass 1. Both races run `.github/scripts/review-race.sh`.
- The AI reviewer often cites stale or nonexistent lines and invents contracts: verify every finding (grep the cited code) before changing anything; decline false positives. A red review job with no findings is usually provider throttling — re-run.
- **A PR body must not claim server-side behavior the code does not implement (2026-11-19, PR #668 OpenCode MINOR).** The body said a partial tool-config save preserves stored keys, but `saveToolConfig` still writes `encrypted_keys: null` when no keys are sent — the fix was prompt-side only (base prompt + MCP description require the complete configuration on every save). A prompt-side mitigation is not a server-side guard; describe it as such.
- **Publish handlers must report dead accounts (2026-11-08, PR #505 OpenCode MAJOR).** Every `lib/upload/*-handler.ts` catch reports provider 401s via `reportAccountUnauthorized(provider, accountId, ownerUserId, error)` so PostHog `publish_account_unauthorized` names the broken account — a handler that only pushes the error string leaves a revoked token invisible. Bluesky never carries a numeric 401: a dead app password surfaces as `BlueskyError` code `invalid_credentials`, which `isUnauthorizedError` treats as unauthorized.
- **Meta answers a dead token with HTTP 400 + code 190, never a 401 (2026-11-16, PostHog fixloop).** `isUnauthorizedError` treats `InstagramApiError`/`FacebookError`/`ThreadsError` with `providerCode === 190` as unauthorized; the libs preserve the code from the Graph error envelope via `readMetaErrorCode` (`lib/meta-error-code.ts`). Never add a numeric `code` field to those errors: `httpStatusOf` reads a numeric `code` as an HTTP status, and 190 is not one. The same incident's `logger.error(..., undefined, ...)` calls recorded bare `Unknown error` $exception events (`logger.toError(undefined)`): always pass the original error as the cause, never `undefined` and never the message string.
- **Guard every `.get` on remote-controlled JSON (2026-11-09, PR #504 OpenCode MINOR).** A non-dict item in the upload API's `results[]` crashed `_targets_from_body`'s synthetic-target fast path (`result.get` on a string) while the sibling branches guarded with `isinstance(item, dict)` — the fast path that skips the guard is the one that crashes.
- **Rename a test when its behavior flips (2026-11-09, PR #504 OpenCode MINOR).** `test_publish_failure_after_claim_returns_slot_to_ready` kept its name after the behavior flipped to staying `publishing`; the name described the exact opposite of the assertions.
- **A scoped API key must see only its personas' data in every new response field (2026-11-10, PR #528 OpenCode MAJOR).** `GET /api/metrics`'s new `coverage` array was computed from `auth.userId` + the URL `persona` param alone, so a persona-scoped key called without `persona=` got coverage items (post ids, persona ids, script angles, account ids, external video ids) for personas outside its scope — while the route's own rows query enforces the scope. Any new field on a scoped route must apply the same scope the route applies to rows (`isScopedApiKey(auth)` + UUID-validated `auth.personaIds`); persona-less (voiceover) posts belong to no scope and stay visible.
- **Dedupe identical list items at the source so React keys cannot collide (2026-11-10, PR #528 OpenCode MINOR).** Two videos of one slot failing on the same account produce identical `publish-failed` coverage items (both carry no video id), and the card key `${postId}:${provider}:${accountId}:${externalId ?? 'failed'}` collides. Keep one item per (provider, account) in the failed-outcomes loop — published entries are keyed by (provider, accountId, video) by the publisher, so only failed entries can collide.
- **A capped read must never feed a scope decision (2026-11-10, PR #528 OpenCode MAJOR).** `fetchCoverage` read personas from the whole `schedules` table capped at 1000 with no filter to the referenced ids, so for a user with more schedules than the cap a post's schedule was missing from the map and degraded to "no persona" — which the scope guard lets through, leaking out-of-scope coverage items to a persona-scoped API key. Read only the ids the posts reference (`.in('id', scheduleIds)`, bounded by `METRICS_ROW_LIMIT`). A schedule that still resolves to nothing is a deleted schedule — and its posts are NOT voiceover by default (see the orphan rule below).
- **A deleted schedule does not make its posts voiceover (2026-11-10, PR #528 OpenCode MAJOR).** `DELETE /api/schedule` deletes only pending/generating/ready slots and then the schedule row, so a published post survives orphaned with `voiceover = false` while its `post_metrics.persona_id` (filled by the 026 trigger at insert, never rewritten) still names its persona. Deriving the coverage persona from the live schedule maps the orphan to null, and a null persona shown as "voiceover" leaks the post to a persona-scoped key the rows query hides it from. The scope guard must use the post's own `voiceover` flag: null persona + not voiceover = hidden from scoped callers.
- **A locale test must assert the formatted value, not the key (2026-11-10, PR #528 OpenCode MINOR).** The pt-BR date test asserted only translation keys (`/metrics\.asOf/`), which the mocked `t()` returns verbatim, so it passed with the en-US branch too and never exercised the pt-BR branch of `formatDate`/`formatDateTime`. Assert the formatted string itself (`/21 de out\. de 2026/`, once per rendered line).
- **Every new failure branch needs its own test (2026-11-10, PR #529 OpenCode MINOR).** The re-open's rows-lookup failure branch (`reopen rows lookup failed`) shipped without a test while the scan-failure branch had one — the reviewer caught the asymmetry. Every `logger.warn` + early-return branch in a collector gets a test asserting both the kept posts and the exact log call.
- **A re-read must mirror the due SQL's "collected" rule, not just its rows (2026-11-10, PR #529 OpenCode MINOR).** The re-open read `post_metrics` rows without `analytics_status` and counted every well-formed row as collected, while `find_post_metrics_due` (migration 039) excludes YouTube rows with a null/`scope_missing` status so the hourly run retries them until the token is reconnected. A late YouTube target whose first snapshot recorded `scope_missing` was therefore never retried by the re-open. Select `analytics_status` and skip those rows in the key-building loop, exactly like the SQL.
- **Fixtures must use shapes production can produce (2026-11-10, PR #529 OpenCode MINOR).** PostgREST materializes every selected nullable column as null, never absent — re-open fixtures that omitted `analytics_status` made `undefined` count as collected, while the closest real shape (null, a pre-039 row) is NOT collected. Three tests depended on the artifact. When a guard branches on null vs a value, every fixture row carries the field.
- **Every `metricsTargets` consumer must report unknown providers (2026-11-10, PR #529 OpenCode MINOR).** The re-open was the only consumer that discarded `found.unknownProviders` without a log, so a late target on a provider the registry does not know yet was skipped silently — the other two consumers (`collectPostMetrics`, `fetchCoverage`) log each one. The re-open now logs `[post-metrics] unknown provider in re-opened publish outcomes` with the post id, before the no-targets skip, and the test pins both the skip and the exact log call.
- **A fixture-shape rule is only done when every live row carries the field (2026-11-10, PR #529 OpenCode MINOR).** The "fixtures must use shapes production can produce" rule was recorded in this PR and three re-open fixtures were fixed, but the Instagram row in 'does not re-open a post whose targets are all collected' still omitted `analytics_status` — the guard short-circuits on YouTube before reading it, so the test stayed green while the artifact class the rule prevents survived. When a rule names a field, grep every fixture row for it before calling the fix done; rows deliberately malformed under test are the only exception.
- **A docstring must state the collected rule, not the row rule (2026-11-10, PR #529 OpenCode MINOR).** `findReopenedPosts`' docstring said a post is due again when it has "no snapshot row", but the code treats a YouTube snapshot with a null/`scope_missing` `analytics_status` as NOT collected, so such a post is due again despite having a row. A reader following the docstring would re-introduce exactly the bug this PR fixed. Say "no collected snapshot row" and point at the mirror.
- **A cap test needs one more candidate than the budget allows (2026-11-10, PR #529 OpenCode MINOR).** 'caps the re-opened posts at the remaining run budget' had a single re-openable candidate for a budget of 1, so deleting the cap branch left the test green — it pinned the budget computation, not the capping its name claims. The fixture now carries a second candidate, and the negative control (cap removed → test fails) pins the mechanism.
- **The re-open budget counts against the processing cap, not the probe limit (2026-11-10, PR #529 OpenCode MAJOR).** `collectPostMetrics` asks `listDuePosts` for `MAX_POSTS_PER_RUN + 1` posts to detect truncation but only processes the first `MAX_POSTS_PER_RUN`; the re-open budget was `limit - posts.length`, so with exactly 50 RPC posts one re-opened post landed at index 50 and was dropped by the slice. The budget is now `MAX_POSTS_PER_RUN - posts.length`, and the cap test pins it with 49 RPC posts + 2 candidates (the negative control — old formula — fails it), plus the 50-post boundary where the scan is skipped.
- **No value imports back across an extraction boundary (2026-11-10, PR #529 OpenCode MINOR).** `post-metrics-reopen.ts` imported `metricsTargets`/`targetKey` from `post-metrics.ts` while `post-metrics.ts` imported `findReopenedPosts` back — a circular import that only worked because both are used inside function bodies. The helpers now arrive as parameters and the module imports only types.
